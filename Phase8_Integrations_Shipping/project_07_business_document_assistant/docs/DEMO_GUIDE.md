# Presenter guide

## Message to the audience

“Product owners should spend their time deciding what the business needs. This workspace organizes raw notes, relevant policy, a consistent document template, and human review. It produces a Word document or a Confluence-style page. Today we use existing Copilot through a manual handoff; this is not an autonomous Copilot backend.”

## Prepare

- Run the app and `python rag_demo.py` using the project README.
- Open Word or a compatible DOCX viewer before the meeting.
- Use only the bundled fictional Northstar Workshop Cobra/FHP room-booking example.
- Choose a fresh browser session for an empty document history.
- Have `outputs/rag-brd-sample-response.json` available for a no-network import demonstration. Explicitly describe it as a fixture if used.
- Keep `outputs/rag-brd.docx` and `outputs/rag-brd.html` as a fallback if the live demo environment fails.

## RAG scenarios

- **Happy path:** Load sample → Workplace → Find business context → confirm → Offline sample → generate. Cobra and FHP definitions appear with `[S101]` and `[S103]` evidence.
- **Ambiguity:** Load sample → All domains → retrieve. FHP has two candidates. Drafting remains disabled. Choose the Workplace meaning and retrieve again.
- **Different domain:** Use title “Instrument checkout”, notes “Apply FHP calibration rules”, and Lab Operations. Expect Field Hardware Protocol with lab sources only.
- **Unknown term:** Add “What does QZX mean for Cobra?” to the sample notes, retrieve again, and show the unknown-term acknowledgment. The draft must preserve the unanswered question.
- **No match:** Use “zzzyyy qqqxxx” for title and notes. No evidence is returned and drafting is blocked.
- **Source freshness:** Explain that fixture changes require restarting this demo. New requests use the rebuilt index; old draft snapshots do not silently change.

## Questions worth demonstrating

- What happens if a selected source is omitted from the imported rules section? Import fails with a corrective message.
- What happens if a user cites `[S99]`? Import rejects the unknown citation.
- Can we publish before approval? The UI disables it and the server rejects it.
- Can an old approval authorize edited content? No; save creates a new revision and clears approval.
- Can a second browser session read the first session's document URL? The server returns 404.
- Will the tool catch every conflicting business rule? No. Offline detection is intentionally narrow; Copilot output also needs review.
- Does a green approval badge mean all open questions are resolved? No. It records a local review acknowledgment, not enterprise sign-off or policy-owner authorization.

## Known limitations to say aloud

This demo does not implement SSO, live Confluence retrieval/publishing, automatic Copilot invocation, a model API, semantic verification, rich Word templates, or production deployment. It demonstrates the product workflow and the contracts needed to add those capabilities.

## Demo acceptance checklist

- [ ] All three document types produce distinct heading structures.
- [ ] Retrieved definitions and policy excerpts appear before drafting.
- [ ] Ambiguous acronyms cannot silently choose a meaning.
- [ ] Copilot brief includes selected sources only, exact template headings, and original notes.
- [ ] Imported response can be reviewed and edited.
- [ ] Word export opens and contains the latest saved revision.
- [ ] Notes and page references are visible in the generation record.
- [ ] Policy disagreement remains a question until a human decides.
- [ ] Publication requires current approval and clearly stays local.
- [ ] Saved edits revoke approval and do not overwrite a published snapshot.

## Feedback to collect

Ask product owners which template sections need the most editing, how often the context selection is wrong, whether Copilot's JSON handoff is manageable, what Word styling is mandatory, and whether their preferred final destination is Word or Confluence. Measure time from notes to a reviewed draft, not merely time to first generation.

## Meeting continuity walkthrough

1. Expand **Track meetings for a project** and click **Load two-meeting demo**.
2. Click **Find business context**. Expand September 1 in the timeline to show the original notes.
3. Show PILOT-1 moving from OPEN to DONE as reported in September 8 notes, RULE-1 moving to IN_PROGRESS, and new REMINDER-1.
4. Highlight ACCESS-1: it was BLOCKED and omitted from September 8, so it carries forward rather than being marked complete.
5. Expand the literal text comparison. Explain that free-form rewording is not understood semantically by this offline implementation.
6. Confirm context and generate an Offline sample or Copilot brief. The draft includes meeting continuity and separate Confluence evidence; the 30-day proposal still conflicts with the 14-day fixture rule.
7. Download Word or simulate Confluence publication. Earlier meetings have M citations and immutable snapshots in the generation record.

For repeatable fallback artifacts run `python meeting_demo.py`. Do not describe reported DONE labels as verified delivery or DECIDED labels as policy-owner approval. Saving an identical meeting again does not duplicate it; comparison excludes same-day/later dates and other browser sessions/projects.
